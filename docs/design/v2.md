# nlir v2 — a small, generic core for learning programs between data and prose

Status: in progress (Oct 2026). This is the working checklist; items are ticked as they land.

## Why

nlir grew a vocabulary of task-specific glyphs (`@` formal, `:` simplify, `?` question,
`#` subject, `~` gist, `>`/`<` expand/shorten…). They read well in a demo but they are
instances, not abstractions. v2 keeps glyphs for a few **generic transforms** — polymorphic
over the values they act on, recognisable from category theory or functional programming —
and moves the instances into a **prelude** of named forms built from those atoms
(`formal={$0 :: 'a formal register'}`).

v2 is also the substrate for **learning programs**: a hill-climbing loop proposes nlir
programs that map structured data (a spec) to prose and back. That needs reproducible
evaluation (a content-addressed record of model calls), backward passes (lenses), a judge that
knows the spirit of the exercise, and visualisations that make a learned program legible.

## A. Semantic core (model-realised)

Values are texts read as concepts. Every operator has a deterministic stub for `--mode det`.

| glyph | name | shape | meaning |
| --- | --- | --- | --- |
| `=>x` | obey | text → text | treat `x` as an instruction and return its result |
| `x :: c` | recast | text × concept → text | `x` re-expressed as kind/register/form `c` (`'formal'`, `'a question'`, `'plain language'`, `'one sentence'`) |
| `x .. a` | project | text × aspect → text | the part of `x` described by `a` (`'its gist'`, `'the subject'`, `'the third item'`); two integers give a range |
| `!x` | dual | text → text | the opposite of `x`; an involution |
| `a & b` / `a \| b` | product / coproduct | text* → text | both / either, as one statement |
| `a Δ b` | change | text × text → text | how `a` becomes `b` |
| `a ▷ d` | apply | text × text → text | `a` changed as `d` describes; `a ▷ (a Δ b) ≈ b` |
| `a ~> b` | entails | text × text → bool | does `a` imply `b` (a preorder on meanings) |
| `a ≈ b` | similar | text × text → number | how fully `b` keeps the meaning of `a`, in [0,1] |

Retired glyphs: `#` `~` `@` `:` `>` `<` postfix `?` `~>?` and the shell-backed `_` echo. Their
meanings live on as prelude forms (`$gist`, `$subject`, `$formal`, `$casual`, `$plain`,
`$question`, `$expand`, `$shorten`).

## B. Structural core (deterministic, polymorphic)

| glyph | class | lists | dicts | text |
| --- | --- | --- | --- | --- |
| `f ↦ x` | Functor map | items | values | — |
| `f ⊘ x` | Foldable fold | items | values | — |
| `f ∘ g` | composition | forms | forms | forms |
| `a ++ b` | Monoid append | concat | right-biased merge | concat |
| `x . k` | lens get | index | key | char |
| `∪ ∩ ∖ ∈` | lattice | sets | keys | substrings |

Plus arithmetic, comparisons, `∧ ∨ ¬`, and the `$…` builtins.

## C. Prelude

Config gains `prelude:` — nlir source evaluated before every program, defining named forms.
The old vocabulary becomes trains over the core, readable and overridable.

## D. Purity and determinism

Model and command calls are the only effects. Each is recorded in a **content-addressed
store** keyed by the operator's full definition (prompt, system frame, resolved model), its
operands and the seed. Replaying a key returns the recorded value, so evaluation is
deterministic and identical calls are free.

- `_cache`: `off` (old behaviour) · `eval` (one evaluation, default) · `persist` (a store file
  shared across runs, evals and hill-climb rounds; it only grows).
- `_cache_file` / `--cache-file` / `NLIR_CACHE_FILE`: the persistent store.
- `_seed`: a namespace. The same seed replays; a new seed draws fresh samples.
- `$draw%(form, n)`: `n` explicit samples of a form under seeds `seed, seed+1, …` — randomness
  is an explicit argument, never ambient.
- Model config `seed: exact | best-effort | none` records whether the provider honours seeds.
  Measured Oct 2026: no reachable hosted model is exact (Claude ignores `seed`; gpt-4.1 accepts it
  and still varies at temperature 0), so the store is the determinism mechanism.
- `--replay strict`: fail on any unrecorded call (audits, CI).

## E. Lenses (backward passes)

Each operator has `get` (the forward value) and `put` (edited result + original inputs → new
inputs), checked against the laws **GetPut** (no edit → no change) and **PutGet** (forward after
put reproduces the edit).

- Bijective deterministic operators invert directly (`$render`/`$fields`, zip/unzip, JSON).
- Lossy deterministic operators (`++`, `$join`, `+`) keep a **complement in the trace**
  (split points, operand values), so forward semantics do not change.
- Model operators get a generic put prompt (instruction, original input, original output, edited
  output → minimally edited input), overridable per operator with `put:`; every put is verified
  by re-running forward.
- Fan-in returns candidate edits per input; fan-out re-runs dependents to show ripples; competing
  edits to one input are conflicts.

## F. Learning loop v2

- Score = output similarity (judged per part) − a program-quality penalty from a **meta-policy
  judge** (codes in the same V/P style as the specs it learns) − a small **complexity** term
  (compressed program size, a Kolmogorov proxy) — no hard limits.
- Worked examples are **bound data** (`$examples`), not program literals.
- Programs carry an **interpretation**: a plain-language reading of what the program does,
  generated and scored for legibility.
- Models: transforms on a small fast model (`luna`: gpt-6-luna, or `haiku`), judging and editing
  on a large one (`sol`: gpt-6.1-sol, or `opus`).

## G. Visualisation

- `nlir show --statements`: a statement-level dataflow graph (named bindings and their
  dependencies, model calls marked) — legible for programs of any size.
- Interactive pan/zoom graphs; the full expression tree on demand per statement.
- Process views: the hill-climb timeline, program diffs, scores by component.
